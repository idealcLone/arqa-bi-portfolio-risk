# Профилирование данных и решения по очистке

Профилировщик: [`scripts/profile_data.py`](../scripts/profile_data.py) — читает сырые CSV,
ничего не меняет, печатает все цифры ниже. Запуск: `python3 scripts/profile_data.py`
(или `make profile`). Все числа в этом файле — вывод этого скрипта.

## Общий объём

| Файл | Строк данных | Ключ | Уникальных ключей |
|---|---|---|---|
| `data/portfolio.csv` | 4060 | (report_date, loan_id) | 4000 |
| `data/fx.csv` | 42 | (date, currency) | 42 |

Срезы: `2026-09-01` — 2030 строк, `2026-10-01` — 2030 строк. По 2000 уникальных
`loan_id` в каждом срезе; состав кредитов в срезах **полностью совпадает**
(0 ушедших, 0 новых), атрибуты кредита (заёмщик, группа, отрасль, программа, валюта,
даты выдачи/погашения) между срезами **не меняются** ни у одного кредита.

## Найденные аномалии и решения

### A1. Полные дубликаты строк — 60 лишних строк
Совпадают все 13 колонок. 30 строк в срезе 01.09 и 30 в срезе 01.10, затронуто
59 кредитов (`L001677` продублирован в обоих срезах). Примеры: `L000008`, `L000087`,
`L000134`, `L000183`, `L000251` (01.09); `L000042`, `L000076`, `L000180` (01.10).
Все четыре кредита, названные в задании (`L001583`, `L000446`, `L002000`, `L001266`),
действительно встречаются дважды в срезе 01.09.

Если не дедуплицировать, портфель завышается на **14 269 161 222,66 ₸** (01.09) и
**12 003 383 283,57 ₸** (01.10) — это ~2% портфеля, то есть ошибка видна в каждой метрике.

**Решение:** дедупликация в `reporting.v_loan_snapshot` оконной функцией
`row_number() over (partition by report_date, loan_id order by ...)` → остаётся одна строка
на (report_date, loan_id). Проверка `checks/`: `raw_rows - mart_rows = 60`.

### A2. Конфликтующие дубликаты (один ключ, разные значения) — 0
Проверено отдельно: ключей (report_date, loan_id) с различающимися значениями колонок —
**0**. То есть дедупликация не теряет информацию и не требует правила выбора «правильной»
строки. Правило `row_number()` всё равно детерминировано (сортировка по всем значимым
колонкам), чтобы повторный прогон давал идентичный результат.

### A3. Списанные кредиты (`written_off = 1`) — 34 строки (33 после дедупа)
После дедупликации: 25 кредитов на 01.09 (6 508 195 216,38 ₸) и 8 кредитов на 01.10
(1 592 848 759,94 ₸). Все 34 строки имеют **остаток > 0** — то есть молча суммировать
`principal_outstanding` нельзя.

**Решение:** по определению задания списанные **исключаются из портфеля**. Строки
**остаются** в `v_loan_snapshot` с флагом `written_off`, но все денежные хелпер-колонки
(`principal_kzt_active`, `par30_kzt`, `par90_kzt`, `npl_kzt`, `provision_kzt`) у них = 0,
а все вьюхи метрик фильтруют `written_off = 0`. Так семантический слой и проверки видят
списанные (можно посчитать их объём), но ни одна мера их не включает.

### A4. Реструктуризации с нулевой просрочкой — 180 строк
`restructured = 1` всего 187 строк; из них по DPD: 01.09 — 92 с `dpd = 0`, 2 с `dpd 1–30`;
01.10 — 88 с `dpd = 0`, 4 с `dpd 1–30`, 1 с `dpd 31–90`.

**Решение:** это не грязь, а бизнес-правило: такие кредиты попадают в **NPL** и получают
ставку провизий **50%** (у NPL приоритет над бакетом DPD). Пересечения
`written_off = 1 и restructured = 1` нет (0 строк), конфликта приоритетов не возникает.

### A5. Кредиты с истёкшим сроком погашения и остатком > 0 — 883 строки
`maturity_date < report_date` при остатке > 0: 883 строки, из них **746 с `days_past_due = 0`**
и 137 с `dpd > 0`. Логически противоречиво (срок прошёл, остаток есть, просрочки нет),
но это ~22% строк, и ни одно определение задания не опирается на `maturity_date`.

**Решение:** **не исключаем и не правим** — определения метрик не используют срок
погашения, а домыслить «правильный» DPD нельзя. Фиксируем как наблюдение и выносим
в дашборд/README как вопрос к источнику. В витрину добавлен флаг `is_past_maturity`,
чтобы объём этого явления был измерим (`select sum(principal_kzt_active) ... where is_past_maturity`).

### A6. Курсы валют: полное покрытие дат срезов
`fx.csv` содержит только `USD`, 42 дня (2026-08-25 … 2026-10-05), по одной строке на дату,
дублей (date, currency) нет, нечисловых и неположительных курсов нет.
Обе даты срезов присутствуют: **01.09.2026 → 478,35**, **01.10.2026 → 482,10**.
В портфеле ровно две валюты: `KZT` (3464 строки) и `USD` (596 строк) — валют без курса нет.

**Решение:** `KZT` конвертируется по курсу 1 (в `fx.csv` его нет и не должно быть),
остальные валюты — join по **точной дате среза** (`rate on report_date`, как требует
определение). Fallback «последний известный курс» намеренно **не** вводится: он не нужен
на этих данных и был бы непротестированным кодом. Вместо него — жёсткая проверка
`checks/02_fx_coverage.sql`: если у любого неKZT-кредита нет курса на дату среза,
пайплайн падает.

## Проверено и аномалий НЕ найдено

Чтобы не создавать ложного впечатления «грязных» данных, ниже — проверки, которые
прошли чисто (все счётчики = 0):

| Проверка | Результат |
|---|---|
| Пустые строки / `NULL` / `'null'`, `'nan'` в любой колонке | 0 |
| Пробелы по краям значений (whitespace) | 0 |
| Регистр валют (`usd`, `Kzt` и т.п.) | 0 — только `KZT`, `USD` |
| Опечатки/варианты в `sector` (6 значений) и `program` (4 значения) | 0 — ровно справочные значения |
| `restructured` / `written_off` вне {0,1} | 0 |
| Нечисловые / отрицательные / нулевые `principal_outstanding` | 0 (все с 2 знаками после точки) |
| Нечисловые / отрицательные `days_past_due` | 0 (min 0, max 419) |
| Непарсящиеся даты, `issue_date > maturity_date`, `issue_date > report_date` | 0 |
| Кредиты в одном срезе и отсутствующие в другом | 0 |
| Разные атрибуты одного `loan_id` между срезами | 0 |
| Один `borrower_id` в нескольких `group_id` | 0 |
| Валюты портфеля, отсутствующие в `fx.csv` | 0 |
| BOM / CRLF / битая кодировка в CSV | нет (UTF-8, LF) |
