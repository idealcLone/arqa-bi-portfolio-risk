# Журнал работы с ИИ-агентом: где ошибся, как поймали, что исправили

Формат: дата — что произошло — как обнаружено — что сделано.
Пишется честно: сюда попадают реальные ошибки, а не придуманные для отчётности.

## 2026-10-14 — `SELECT *` внутри CTE, вопреки собственной конвенции
**Что было.** В `reporting.v_loan_snapshot` агент (я) написал CTE `classified as (select c.*, ...)`.
В `CLAUDE.md` при этом зафиксировано правило «явные списки колонок, никогда `SELECT *` в вьюхах».
**Как обнаружено.** Проверка `grep -n "c\.\*" sql/reporting/*.sql` после написания файла.
**Фикс.** CTE переписан с явным перечислением 20 колонок. Правило теперь проверяется
грепом перед коммитом.
**Почему важно.** `SELECT *` во вьюхе ломает контракт при изменении нижнего слоя:
добавили колонку в `raw` — поехал состав колонок витрины и семантической модели.

## 2026-10-14 — негативный тест был поставлен неправильно, а не проверка
**Что было.** Чтобы убедиться, что `checks/02_fx_coverage.sql` умеет падать, я подменил курс
в `raw.fx` (`update raw.fx set rate_kzt = 999 where date = '2026-09-01'`) и ожидал, что
проверка 2.4 («использован курс именно на дату среза») упадёт. Она прошла зелёной,
и первая мысль была «проверка тавтологична и бесполезна».
**Как обнаружено.** Негативным тестом, но вывод из него я сначала сделал неверный.
**Разбор.** Проверка 2.4 сравнивает курс, использованный витриной, с `raw.fx` на ту же дату.
Правка самого `raw.fx` меняет **обе** части сравнения одновременно — поймать её этот
ассерт в принципе не может. А вот ошибку **во вьюхе** он ловит: тест 3b подменил join на
`f.rate_date = d.report_date - 1`, и проверка упала (`Кредитов без курса на дату среза: 3412`).
**Что сделано.** Проверка оставлена как есть (она ловит тот класс ошибок, для которого
написана), но её область действия зафиксирована в `docs/verification.md`: ассерты в `checks/*.sql`
ловят ошибки **логики вьюх**, а искажение исходных данных ловит только независимый пересчёт
из CSV (`checks/independent_recompute.py`), который строит свою карту курсов из файла.
**Вывод для проекта.** Один слой проверок недостаточен: SQL-ассерты и пересчёт вне SQL
закрывают разные классы ошибок. Это и есть ответ на вопрос «как вы проверяли цифры».

## 2026-10-14 — профиль данных оказался чище, чем описание задачи
**Что было.** В постановке перечислен длинный список ожидаемой «грязи»: регистр и пробелы
в валютах/отраслях, пустые строки, отрицательные остатки, валюты без курса, несовпадающий
состав срезов. Соблазн был описать их в `docs/data_quality.md` как найденные (список-то дан).
**Как обнаружено.** `scripts/profile_data.py` — все эти счётчики вышли нулевыми.
Реальных аномалий четыре: 60 полных дублей, 34 списанных с остатком > 0,
180 реструктуризаций с DPD = 0, 883 строки с истёкшим сроком при остатке > 0.
**Что сделано.** В `docs/data_quality.md` отдельная таблица «Проверено и аномалий НЕ найдено»
с нулями — чтобы не выдавать чужой список за собственные находки, но и показать, что проверка
была. Ни одно правило очистки не написано «на всякий случай» под несуществующую проблему.

## 2026-10-14 — отказ от fallback-а по курсам, который никогда не сработает
**Что было.** Первым желанием было сделать поиск курса «последний известный на дату ≤ даты среза»
как более «надёжный».
**Разбор.** На этих данных курсы есть на обе даты среза (01.09 → 478,35; 01.10 → 482,10),
то есть ветка fallback-а не исполнилась бы ни разу — непротестированный код в расчёте денег.
**Что сделано.** Join строго по дате среза + жёсткий ассерт `checks/02_fx_coverage.sql`,
который валит пайплайн, если у неKZT-кредита нет курса на дату среза. Решение согласовано
с заказчиком перед сборкой витрины.

## 2026-10-14 — профиль смотрел «внутри среза» и пропустил возврат списаний
**Что было.** Первый профиль (`scripts/profile_data.py`) проверял аномалии внутри каждого
среза и сопоставимость состава кредитов, но **не сравнивал флаги между датами**. Поэтому
в `docs/data_quality.md` сначала не было аномалии A7: 23 кредита, списанных на 01.09,
на 01.10 снова числятся действующими (`written_off` 1 → 0). Списание необратимо,
так что это либо ошибка источника, либо нестандартное восстановление долга.
**Как обнаружено.** Не проверкой, а разбором результата: при подготовке выводов для
риск-комитета бросилось в глаза, что списанных стало 25 → 8, хотя списания должны
накапливаться. Запрос по переходам флагов подтвердил: `1 → 0` у 23 кредитов на
**5 675 019 588,05 ₸** (1,17% портфеля на 01.10), из них 2 960 417 548,60 ₸ в NPL.
**Фикс.** В профилировщик добавлен блок 16 «Переходы флагов между срезами»;
аномалия описана как A7; эффект на сопоставимость вынесен в README отдельным выводом.
Правило расчёта не менялось: флаг применяется на дату среза.
**Вывод для проекта.** Профилировать надо не только срез, но и **переходы между срезами** —
иначе метрика «улучшилась» по причине, которой в реальности не было. Ни один из 7 SQL-ассертов
это бы не поймал: с точки зрения каждой отдельной даты данные идеально консистентны.

## 2026-10-14 — DROP TABLE ломал второй прогон пайплайна
**Что было.** `sql/raw/00_schema.sql` начинался с `drop table if exists raw.portfolio`.
Первый прогон проходил (вьюх ещё нет), второй падал:
`cannot drop table raw.portfolio because other objects depend on it`.
То есть заявленная в CLAUDE.md идемпотентность на деле не работала.
**Как обнаружено.** `scripts/check_idempotency.sh` — скрипт, который гоняет весь пайплайн
дважды. Ошибка вылезла на первом же запуске скрипта.
**Фикс.** `create table if not exists` + `TRUNCATE` при загрузке, плюс блок проверки
контракта структуры: если колонки в БД разошлись с DDL, пайплайн падает с подсказкой
`make down && make all`. Вариант `DROP ... CASCADE` отвергнут: он сносит весь слой
reporting ради перезагрузки данных.

## 2026-10-14 — спеки Vega-Lite: временной формат на строковом поле и width:"container" в фасетах
**Что было.** Графики рендерились пустыми карточками. Две причины:
(1) `"format": "%d.%m.%Y"` стоял на поле `report_date` типа `ordinal` — Vega пытается
разобрать это как числовой формат и падает с `invalid format: %d.%m.%Y`;
(2) `"width": "container"` не поддерживается в фасетных спеках (`column`) и давал
`WARN Width "container" only works for single views and layered views`, а в карточках
грида ширина схлопывалась в 0.
**Как обнаружено.** Скриншот показал пустые карточки, а запуск headless Chrome с
`--enable-logging=stderr` показал ровно эти две ошибки в консоли.
**Фикс.** Формат даты перенесён в выгрузку: `to_char(report_date, 'DD.MM.YYYY')` как
колонка `report_date_label` (формат живёт в SQL, а не в спеке); в спеках заданы явные
размеры. `scripts/screenshot.sh` теперь **падает**, если в консоли есть ошибки или
отрисовано меньше 8 графиков — чтобы «пустой дашборд» больше не мог доехать до README.

## 2026-10-14 — сквозная сверка показала «дубль в витрине», которого не было
**Что было.** Первая версия `checks/07_spot_checks.sql` выбирала кредиты-кейсы через
`UNION ALL`, и один и тот же кредит (L001743) попал сразу в два кейса — «валютный» и
«реструктуризация с DPD = 0». На join это дало по две строки на кредит, и вывод выглядел
так, будто витрина не дедуплицирована.
**Как обнаружено.** Глазами по выводу + тем, что check 01 (уникальность ключа витрины)
при этом был зелёным — одно из двух утверждений обязано было быть ложным.
**Фикс.** Кейсы сделаны взаимоисключающими (валютный кейс теперь требует
`restructured = 0 and days_past_due = 0`), выбор вынесен в одну временную вьюху
`spot_cases`, и добавлен ассерт «один кредит не может попасть в два кейса».
**Вывод для проекта.** Прежде чем поверить, что сломана витрина, стоит проверить,
не сломан ли сам диагностический запрос — особенно когда два ассерта противоречат друг другу.

## 2026-10-14 — вывод для риск-комитета был сформулирован с неверным знаком эффекта
**Что было.** Черновик вывода №1 в README назывался «треть улучшения — возврат ранее
списанных кредитов», то есть утверждал, что вернувшиеся из списания кредиты **улучшили**
отчётный NPL. Это было написано «по интуиции»: раз в портфель вернулись проблемные кредиты,
значит они как-то приукрасили картину.
**Как обнаружено.** Перед коммитом посчитал сопоставимые доли запросом вместо того, чтобы
оставить утверждение как есть. Вернувшиеся кредиты добавляют 5,68 млрд ₸ к знаменателю
и 2,96 млрд ₸ к числителю NPL, и в сумме **ухудшают** показатель: без них NPL на 01.10
был бы 9,51% вместо 10,01% (−0,50 п.п.), PAR90 — 3,90% вместо 4,46%.
**Фикс.** Заголовок и текст вывода переписаны, сопоставимые NPL/PAR30/PAR90 добавлены
в автогенерируемый блок README (`scripts/render_readme.py`), чтобы утверждение опиралось
на выводимую цифру, а не на рассуждение.
**Вывод для проекта.** Качественные утверждения («улучшило», «ухудшило», «основной драйвер»)
надо выводить из запроса ровно так же, как сами цифры. Это самая опасная категория ошибок:
все числа в отчёте верные, а вывод из них — противоположный.

## 2026-10-14 — генератор README делил проценты на 100
**Что было.** В `scripts/render_readme.py` колонки `*_chg_pp` (уже в процентных пунктах)
дополнительно делились на 100, и в итоговой таблице изменения выглядели как
`PAR30 −0,02 п.п.` вместо `−1,72 п.п.`
**Как обнаружено.** Сверкой сгенерированной таблицы с выводом `make metrics` —
числа не сошлись на два порядка.
**Фикс.** Деление убрано, в `pp()` добавлена строка документации про единицы измерения,
а места, где на вход идёт разница долей, домножены на 100 явно.
**Почему попало сюда.** Это ровно та ошибка, ради которой в проекте есть правило
«ни одной цифры руками»: генератор избавляет от опечаток, но сам может врать в единицах,
поэтому его вывод тоже надо сверять с источником.

## 2026-10-14 — проверка прода сама соврала из-за float
**Что было.** После деплоя сверял JSON на проде с `reporting.v_portfolio_metrics` и получил
8 «расхождений» в долях: `прод=0.1204940600828242` против `БД=0.12049406008282420658`.
Первая реакция — искать потерю точности в выгрузке.
**Как обнаружено.** Разрядность обрезалась ровно там, где заканчивается точность double:
`json.load` в Python по умолчанию парсит числа в `float`, то есть расхождение внёс сам
проверяющий скрипт, а не пайплайн. Сами JSON-файлы содержат полную точность numeric.
**Фикс.** Сверка делается с `json.load(..., parse_float=decimal.Decimal)` — после этого
все 12 значений совпали точно. Суммы в ₸ «совпадали» и во float-версии только потому,
что в них меньше значащих цифр, — то есть ошибка пряталась именно в долях.
**Вывод для проекта.** Деньги и доли нельзя прогонять через float даже в одноразовом
проверочном скрипте: проверка, которая сама теряет точность, создаёт ложные тревоги
и подрывает доверие к настоящим проверкам.

## 2026-10-14 — скрипты затирали переменные окружения из `.env` (поймал CI)
**Что было.** `run.sh`, `scripts/export_dashboard_data.sh` и `scripts/spot_check.sh` делали
`set -a; . ./.env; set +a`, а при отсутствии `.env` копировали его из `.env.example`.
Локально это работает, а в GitHub Actions параметры подключения приходят из workflow —
и скрипт молча подменял их значениями из `.env.example` (`POSTGRES_PASSWORD=change_me`).
Сборка падала на шаге выгрузки: `password authentication failed for user "arqa"`.
**Как обнаружено.** Первым же прогоном CI после пуша. Локально ошибка не воспроизводилась
в принципе — именно ради таких случаев CI и добавлялся.
**Фикс.** Общий загрузчик `scripts/load_env.sh`: переменные из `.env` экспортируются
**только если не заданы снаружи**. Проверено обоими сценариями — с внешней переменной
(остаётся внешняя) и без неё (берётся из `.env`).
**Вывод для проекта.** `set -a; . ./.env` — приоритет файла над окружением, то есть
ровно наоборот тому, как ведут себя все нормальные конфиги. В CI это выглядит как
«проблема с паролем», хотя дело в порядке приоритетов.

## 2026-10-14 — зависание генератора README в CI: сначала поставил неверный диагноз
**Что было.** `scripts/render_readme.py` локально отрабатывал за 1 секунду, а в CI шаг
висел и падал по таймауту (`exit code 124`). Два блока README (мост NPL и сопоставимость)
считались через self-join двух копий `reporting.v_loan_snapshot`, а внутри одного из них
стоял ещё и `... where loan_id not in (select loan_id from ret)`.

**Диагноз №1 (неверный).** `EXPLAIN ANALYZE` локально показал `Filter: (NOT (hashed SubPlan 1))`
— Postgres захешировал подзапрос. Хеширование зависит от `work_mem`, иначе подзапрос
пересчитывается на каждую строку. Я решил, что дело в `NOT IN`, заменил его на `NOT EXISTS`
(анти-join), убедился, что цифры не изменились, и запушил.
**Результат: CI упал ровно так же.** То есть объяснение было правдоподобным, но неверным:
я нашёл реальную потенциальную проблему и выдал её за причину, не проверив.

**Как нашёл настоящую причину.** Добавил `timeout` на каждую команду шага, `timeout-minutes`
на job и печать времени по каждому блоку README. После этого стало видно: выгрузка
занимает 0,6 с, а висит именно генерация, и виноват не фильтр, а **self-join витрины** —
`v_loan_snapshot` сама по себе дедупликация с оконной функцией + join курсов, и при
соединении двух её копий планировщик в CI выбирал план, пересчитывающий витрину многократно.
Локально выбирался другой план, поэтому ошибка не воспроизводилась в принципе.

**Фикс.** Оба блока переписаны на **один проход** по витрине с условной агрегацией
(`sum(...) filter (where report_date = ...)`, `bool_or(...)`) и группировкой по `loan_id`:
витрина читается ровно один раз, и результат не зависит от выбора плана.
`NOT EXISTS` при этом оставлен — он всё равно правильнее `NOT IN`.
Цифры в README после перестройки не изменились (`diff` пуст).
В CI блоки теперь: `npl_bridge 0,14 с`, `comparability 0,38 с`, весь прогон — 39 секунд.

**Выводы для проекта.**
1. Правдоподобное объяснение — не диагноз. Прежде чем чинить, надо получить
   доказательство, что причина именно эта (здесь — измерение времени по блокам).
2. Шаг CI без таймаута не диагностируется: он «висит» вместо «упал вот тут».
3. Self-join вьюхи, которая сама содержит оконные функции и join, — дорогая конструкция,
   чувствительная к плану. Если нужны данные двух срезов рядом, дешевле и надёжнее
   один проход с условной агрегацией.
4. `NOT IN` по подзапросу всё равно стоит заменять на `NOT EXISTS`: корректность
   одинаковая, а производительность у `NOT IN` зависит от настроек сервера.
