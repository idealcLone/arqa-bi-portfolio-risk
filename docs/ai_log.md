# Журнал работы с ИИ-агентом: где ошибся, как поймали, что исправили

Формат: дата — что произошло — как обнаружено — что сделано.
Пишется честно: сюда попадают реальные ошибки, а не придуманные для отчётности.

## 2026-10-14 — `SELECT *` внутри CTE, вопреки собственной конвенции
**Что было.** В `reporting.v_loan_snapshot` агент (я) написал CTE `classified as (select c.*, ...)`.
В `CLAUDE.md` при этом зафиксировано правило «явные списки колонок, никогда `SELECT *` в вьюхах».
**Как обнаружено.** Проверка `grep -n "c\.\*" sql/reporting/*.sql` после написания файла.
**Фикс.** CTE переписан с явным перечислением 20 колонок. Правило теперь проверяется
грепом перед коммитом.
**Почему важно.** `SELECT *` во вьюхе ломает контракт при изменении нижнего слоя:
добавили колонку в `raw` — поехал состав колонок витрины и семантической модели.

## 2026-10-14 — негативный тест был поставлен неправильно, а не проверка
**Что было.** Чтобы убедиться, что `checks/02_fx_coverage.sql` умеет падать, я подменил курс
в `raw.fx` (`update raw.fx set rate_kzt = 999 where date = '2026-09-01'`) и ожидал, что
проверка 2.4 («использован курс именно на дату среза») упадёт. Она прошла зелёной,
и первая мысль была «проверка тавтологична и бесполезна».
**Как обнаружено.** Негативным тестом, но вывод из него я сначала сделал неверный.
**Разбор.** Проверка 2.4 сравнивает курс, использованный витриной, с `raw.fx` на ту же дату.
Правка самого `raw.fx` меняет **обе** части сравнения одновременно — поймать её этот
ассерт в принципе не может. А вот ошибку **во вьюхе** он ловит: тест 3b подменил join на
`f.rate_date = d.report_date - 1`, и проверка упала (`Кредитов без курса на дату среза: 3412`).
**Что сделано.** Проверка оставлена как есть (она ловит тот класс ошибок, для которого
написана), но её область действия зафиксирована в `docs/verification.md`: ассерты в `checks/*.sql`
ловят ошибки **логики вьюх**, а искажение исходных данных ловит только независимый пересчёт
из CSV (`checks/independent_recompute.py`), который строит свою карту курсов из файла.
**Вывод для проекта.** Один слой проверок недостаточен: SQL-ассерты и пересчёт вне SQL
закрывают разные классы ошибок. Это и есть ответ на вопрос «как вы проверяли цифры».

## 2026-10-14 — профиль данных оказался чище, чем описание задачи
**Что было.** В постановке перечислен длинный список ожидаемой «грязи»: регистр и пробелы
в валютах/отраслях, пустые строки, отрицательные остатки, валюты без курса, несовпадающий
состав срезов. Соблазн был описать их в `docs/data_quality.md` как найденные (список-то дан).
**Как обнаружено.** `scripts/profile_data.py` — все эти счётчики вышли нулевыми.
Реальных аномалий четыре: 60 полных дублей, 34 списанных с остатком > 0,
180 реструктуризаций с DPD = 0, 883 строки с истёкшим сроком при остатке > 0.
**Что сделано.** В `docs/data_quality.md` отдельная таблица «Проверено и аномалий НЕ найдено»
с нулями — чтобы не выдавать чужой список за собственные находки, но и показать, что проверка
была. Ни одно правило очистки не написано «на всякий случай» под несуществующую проблему.

## 2026-10-14 — отказ от fallback-а по курсам, который никогда не сработает
**Что было.** Первым желанием было сделать поиск курса «последний известный на дату ≤ даты среза»
как более «надёжный».
**Разбор.** На этих данных курсы есть на обе даты среза (01.09 → 478,35; 01.10 → 482,10),
то есть ветка fallback-а не исполнилась бы ни разу — непротестированный код в расчёте денег.
**Что сделано.** Join строго по дате среза + жёсткий ассерт `checks/02_fx_coverage.sql`,
который валит пайплайн, если у неKZT-кредита нет курса на дату среза. Решение согласовано
с заказчиком перед сборкой витрины.
