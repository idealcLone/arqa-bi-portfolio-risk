# CLAUDE.md — arqa BI: риск-сводка кредитного портфеля

## Цель проекта
Витрины DWH + семантический слой + дашборд по кредитному портфелю на двух срезах
(2026-09-01 и 2026-10-01). Стек: PostgreSQL 16 (docker), YAML-семантика, Vega-Lite v5,
статическая HTML-страница. Тестовое задание: https://jobs.arqa.cc/bi (раздел «Мини-проект»).

## Бизнес-определения (реализовать ровно так)
- **Портфель** = Σ `principal_outstanding`, переведённая в KZT по курсу **на дату среза**,
  **без списанных** кредитов (`written_off = 1` исключаются из всех метрик).
- **PAR30** = доля портфеля с `days_past_due > 30` (строго больше).
- **PAR90** = доля портфеля с `days_past_due > 90` (строго больше).
- **NPL** = доля портфеля с `days_past_due > 90` **ИЛИ** `restructured = 1`.
- **Провизии** = остаток × ставка:
  - 50% — если NPL (`dpd > 90` или `restructured = 1`) — **приоритет у NPL**;
  - 10% — если `31 <= dpd <= 90` и не NPL;
  - 1% — если `dpd <= 30` и не NPL.
  Реструктурированный кредит с DPD = 0 получает 50%.
- **Концентрация** = доля **топ-10 групп** связанных заёмщиков (`group_id`) в портфеле,
  ранжирование по KZT-экспозиции внутри каждой даты.
- **Единый знаменатель**: все доли считаются от KZT-портфеля той же даты (без списанных).
- Цифры в макете на сайте (312,4 млрд ₸, PAR30 8,7% …) — **условные**, не подгонять.

## Конвенции
1. **Идемпотентность.** Загрузка raw = `TRUNCATE` + `\copy` в одной транзакции.
   Все вьюхи — `CREATE OR REPLACE VIEW`. Повторный `make all` даёт идентичный результат.
2. **Деньги — `numeric`**, никогда `float`/`real`/`double precision`.
3. **Нет магических чисел.** Пороги DPD и ставки провизий живут в одном месте:
   `reporting.v_params`. Бакет DPD и ставка провизии считаются **одним** `CASE`
   в `reporting.v_loan_snapshot` и переиспользуются всюду.
4. **SQL-стиль**: явные списки колонок (никогда `SELECT *` в вьюхах), CTE вместо вложенных
   подзапросов, комментарии к каждому бизнес-правилу.
5. **Правило проверки: никогда не называть цифру, которую не получил из запроса или скрипта.**
   README, коммиты, ответы в чате — только вывод запроса, скопированный как есть.
6. Каждая цифра трассируется до вьюхи: в README/дашборде нет чисел, вбитых руками.
   Дашборд читает только JSON, выгруженный из `reporting.*`.
7. **Дашборд сверяется с CSV напрямую** (`checks/dashboard_vs_csv.py`): цепочка
   «источник → витрина → выгрузка → график» должна быть замкнута, иначе ошибка в шаге
   выгрузки не видна ни одной другой проверке. Деньги сравниваются точно, доли — с допуском
   1e-18 (деление в Postgres даёт ~20 значащих цифр, в Python Decimal — 28).
8. **Независимая сверка**: `checks/independent_recompute.py` пишется от определений выше,
   читает сырые CSV напрямую, не переиспользует SQL-логику. Расхождение > 0.01 ₸ / 1e-9 доли — падение.
9. Секреты не коммитятся: креды БД в `.env` (в `.gitignore`), в репозитории `.env.example`.

## Грабли, на которые уже наступали (не повторять)
- **Не `DROP TABLE` в `sql/raw/00_schema.sql`** — на таблицах висят вьюхи reporting,
  второй прогон падает. Только `create table if not exists` + `TRUNCATE` при загрузке.
- **В спеках Vega-Lite нет временного формата на строковом поле**: дата приходит из выгрузки
  готовой подписью `report_date_label` (`to_char(report_date,'DD.MM.YYYY')`).
  `width: "container"` не работает в фасетных спеках — ширина задаётся явно.
- **`*_chg_pp` уже в процентных пунктах** — не делить на 100 при форматировании.
- **Профилировать не только срез, но и переходы между срезами** (так нашлась аномалия A7:
  23 кредита вернулись из списания).
- **Качественные выводы тоже выводить запросом**: формулировка «улучшило/ухудшило»
  один раз уже оказалась с обратным знаком.

## Как запустить
```bash
make all         # БД → схемы → CSV → вьюхи → проверки → семантика → выгрузка JSON → README
make profile     # профилирование сырых данных
make checks      # только проверки
make metrics     # показать v_portfolio_metrics
make serve       # дашборд на localhost:8000
make screenshot  # пересобрать docs/dashboard.png (падает при ошибках в консоли)
make down        # остановить БД

./scripts/check_idempotency.sh   # двойной прогон + побайтовое сравнение выгрузки
./scripts/spot_check.sh          # сквозная сверка отдельных кредитов
```
`make all` идемпотентен и запускается дважды без ошибок.

## Слои reporting
- `v_params` — пороги и ставки (одна строка).
- `v_fx` — нормализованные курсы (dedup по (date, currency)).
- `v_loan_snapshot` — очищенная витрина, 1 строка на (report_date, loan_id):
  дедупликация, нормализация текста, `principal_kzt`, флаги `is_par30/is_par90/is_npl`,
  `provision_rate`, `provision_kzt`, `dpd_bucket`, хелпер-колонки `*_kzt` для семантики.
- `v_portfolio_metrics` — 1 строка на дату + изменение к 2026-09-01.
- `v_metrics_by_sector`, `v_metrics_by_program`, `v_top_groups`.
